# Development guide

## Prerequisites

| Tool | Version | Notes |
|------|---------|-------|
| Python | 3.11+ | Developed on 3.13 |
| Node.js | 20+ | Developed on 22 |
| PostgreSQL | 16+ | With the `pgvector` extension available |

```bash
# macOS
brew install postgresql@17 pgvector
brew services start postgresql@17
createdb atlas
createdb atlas_test
```

`pgvector` is enabled by the first migration, so no manual `CREATE EXTENSION` is needed —
only the extension files must be installed.

## Backend

```bash
cd backend
python3 -m venv .venv
./.venv/bin/pip install -e ".[dev]"

cp .env.example .env
# Generate a real key:
python3 -c "import secrets; print('SECRET_KEY=' + secrets.token_urlsafe(48))"

./.venv/bin/alembic upgrade head
./.venv/bin/uvicorn atlas.main:create_app --factory --reload
```

API on <http://localhost:8000>. Interactive docs at `/docs` (disabled in production).

Note the `--factory` flag: `atlas.main` deliberately exposes `create_app()` rather than a
module-level `app`, so importing the module has no side effects and tests can build an
application with their own settings.

### Tests

```bash
./.venv/bin/pytest              # whole suite
./.venv/bin/pytest -k auth      # one area
./.venv/bin/pytest -x -q        # stop at first failure
```

Tests run against `atlas_test`, which is migrated down to base and back up once per session.
Each test truncates the tables it touched, so tests cannot depend on each other's data.

Point the suite elsewhere with `TEST_DATABASE_URL`.

### Lint and types

```bash
./.venv/bin/ruff check . --fix
./.venv/bin/ruff format .
./.venv/bin/mypy atlas
```

All three must be clean before a commit.

### Migrations

```bash
./.venv/bin/alembic revision --autogenerate --rev-id 0002 -m "papers and chunks"
./.venv/bin/alembic upgrade head
./.venv/bin/alembic downgrade -1
```

Revision ids are sequential (`0001`, `0002`, …) rather than random hashes, so the migration
directory reads in order.

**Always read an autogenerated migration before applying it.** Autogenerate does not detect
everything — extensions, index method changes, and data backfills have to be written by hand.
Verify `downgrade()` actually reverses `upgrade()`; the test suite runs a full
`downgrade base` → `upgrade head` cycle, so a broken downgrade fails the suite.

Every model must be imported in `atlas/models/__init__.py`. Autogenerate compares against
`Base.metadata`, and a model nothing imports is invisible to it — the symptom is a migration
that silently drops the table.

### Filling the catalog

The Discover page searches `catalog_papers`, which starts empty. Fill it from arXiv:

```bash
cd backend
python -m scripts.harvest_arxiv --set cs --max-records 20000   # a few minutes
python -m scripts.harvest_arxiv --set cs                       # all of computer science
python -m scripts.harvest_arxiv                                # all of arXiv
```

Measured: about 66 papers a second (arXiv asks for three seconds between requests, and that is
obeyed), and 3.4KB of database each.

| | Time | Disk |
|---|---|---|
| 100,000 papers | ~25 min | ~340MB |
| 500,000 papers | ~2 hours | ~1.7GB |
| 2,600,000 papers (all of arXiv) | ~11 hours | ~8.7GB |

Check `df -h` before the last one.

```bash
python -m scripts.harvest_arxiv --all      # every archive in turn, ~2.6M papers
```

**Stopping is safe at any point.** Every page is committed as it lands, and the resumption
token is written to `backend/.harvest-token`:

```bash
python -m scripts.harvest_arxiv --resume "$(cat .harvest-token)"
```

Re-harvesting a range that overlaps an earlier run corrects the existing rows rather than
duplicating them, so resuming is safe even when a token rewinds.

### Papers arXiv does not have

arXiv is preprints, and overwhelmingly physics, mathematics and computer science — no
medicine, no chemistry, no humanities. OpenAlex indexes over a hundred million works across
every field, free and without a key:

```bash
python -m scripts.harvest_openalex \
  --filter "has_abstract:true,type:article,primary_topic.field.id:fields/27" \
  --max-records 50000 --mailto you@example.com
```

A hundred million rows would be about 300GB, so this takes **slices** — a field, a date range,
a topic — and which slices is your decision. Useful filters are listed in the script's `--help`.

Give `--mailto`: OpenAlex puts named clients in a faster queue, and free services stay free
partly because heavy users say who they are.

One difference worth knowing: an arXiv id always resolves to a free PDF, an OpenAlex work only
when it is open access. Entries without one show *No free full text* rather than offering an
import that would fail.

The run refreshes the table's statistics as it goes. That is load-bearing rather than tidiness
— see [`decisions.md`](decisions.md) D13 — so a harvest interrupted by Ctrl-C or a dropped
connection still does it on the way out.

## Frontend

```bash
cd frontend
npm install
cp .env.example .env.local
npm run dev
```

App on <http://localhost:3000>.

```bash
npx tsc --noEmit    # type-check
npm run lint
npm run build       # type-checks and prerenders; catches server/client boundary errors
```

`npm run build` is the real gate. It prerenders every static route, so mistakes that only
appear during server rendering — a client hook in a server component, a component that throws
without a browser — surface there and not in `dev`.

## Conventions

**Backend**

- Business rules live in `services/`, not in route handlers. A service must be callable from a
  worker or a script with no HTTP request present.
- Raise errors from `core/errors.py`. Never construct an error response by hand.
- `detail=` on an error is for the logs; `message` is what the user reads. Detail is never
  serialised into a response.
- Nothing reads `os.environ` outside `core/config.py`.
- Never log credentials, tokens, or document contents.

**Frontend**

- Server components by default. Add `"use client"` only when a component needs state, effects,
  or event handlers.
- Style with design tokens (`text-ink-muted`, `bg-surface`), never raw colours. A hard-coded
  hex will be wrong in one of the two themes.
- Interactive elements need a visible focus state, an accessible name, and keyboard operation.
- Every async surface needs all four states: loading, empty, error, and content.

**Commits**

Conventional prefixes: `feat:`, `fix:`, `refactor:`, `docs:`, `test:`, `chore:`. The subject
says what changed; the body says why, when why is not obvious.

## Troubleshooting

**`relation "users" does not exist` in tests** — the test database has not been migrated.
Confirm `atlas_test` exists; the session fixture migrates it automatically.

**`database_url must use the postgresql+asyncpg:// scheme`** — the DSN is missing the async
driver. Atlas is async end to end and will not run on `psycopg2`.

**Autogenerate produces an empty migration** — the model is not imported in
`atlas/models/__init__.py`.

**Frontend requests fail with a CORS error** — `CORS_ORIGINS` in `backend/.env` must exactly
match the frontend origin, scheme and port included. A wildcard is not valid here: cookie
authentication requires `allow_credentials`, and the two are mutually exclusive.

**Signed in but every request 401s** — check that `NEXT_PUBLIC_API_URL` and `CORS_ORIGINS`
agree, and that the browser is not blocking third-party cookies for `localhost`.

## Browser tests

The API suite covers behaviour; these cover what only exists in a browser — whether the PDF
paints, whether text can be selected out of it, whether a highlight survives the round trip,
and whether any page spills sideways on a phone.

They need more setup than the unit suite, so they are run deliberately rather than as part of
`npm test`. A test that cannot run on a fresh checkout gets skipped, and a skipped test rots.

```bash
# three things must be up
uvicorn atlas.main:create_app --factory     # the API
python scripts/seed_demo.py                 # the demo account these tests sign in as
npm run dev                                 # the web app

npm run e2e                                 # then, in a fourth terminal
```

A setup project signs in once and every test reuses that session. Per-test sign-in meant
eighteen logins a minute, which the account's own rate limit refused — correctly, and the
suite was unrunnable against a properly configured server until it was fixed.

If the setup step fails with a 429, an earlier run has spent the login allowance. Restarting
the API clears the counters, since they are held in memory.

## Running it in containers

```bash
cp backend/.env.example .env    # then set SECRET_KEY, and an API key if you want the assistant
docker compose up --build
```

That brings up PostgreSQL with `pgvector`, runs the migrations, starts the API on `:8000`, and
serves the web app on `:3000`.

A few decisions worth knowing:

- **Migrations run in the API's start command**, not in an entrypoint script. A failed
  migration then stops the container rather than leaving it serving against a schema it does
  not match.
- **The API waits for the database to be *healthy*, not merely started.** Postgres accepts
  connections a moment after its process appears, and starting before then fails in a way that
  reads like a configuration error.
- **`SECRET_KEY` has no default.** Compose refuses to start without it, because a default
  secret is one that ends up in production.
- **Shared rate limiting is on**, since more than one worker would otherwise each keep their
  own counters.
- **Uploaded PDFs live on a volume.** A container is disposable; a library is not.
- **Both images run as an unprivileged user.** Nothing here needs root, and PDF parsing on
  files someone else supplied is exactly the code to be careful about.

**Not a production deployment.** It serves plain HTTP and has no TLS, no backups, and no
process supervision beyond Docker's own. It exists so that running Atlas is one command, and so
what runs elsewhere is what runs here.

**Unverified locally.** Docker is not installed on the machine this was written on, so the
compose file has been checked for structure and the Dockerfiles for the paths they reference,
but neither image has been built. That is the one part of this repository that has not been run.
