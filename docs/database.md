# Database

PostgreSQL 16+ with `pgvector`. One store for relational data and embeddings — the reasoning
is in [`decisions.md`](decisions.md) D1.

Migrations live in `backend/alembic/versions`, numbered sequentially. The schema below is what
exists today; later milestones add tables rather than reshaping these.

---

## Conventions

- **UUID primary keys**, generated by `gen_random_uuid()`. Identifiers appear in URLs, and a
  sequential integer would leak how many users or papers exist.
- **`created_at` / `updated_at`** on every entity, with database defaults so a row written by a
  migration or a script is stamped the same way as one written by the API.
- **Named constraints** via a metadata naming convention, so Alembic can drop by name.
- **Enums as `VARCHAR` + `CHECK`**, not native PostgreSQL enum types. Adding a value is a plain
  migration rather than an `ALTER TYPE`, and the column stays readable in `psql`.
- **Ownership is a column, not a convention.** Every user-owned table carries `owner_id` with
  `ON DELETE CASCADE`, and every query filters on it.

---

## Tables

### `users`, `user_sessions`

Accounts and browser sessions. A session stores only the SHA-256 hash of its refresh token,
plus `previous_token_hash` so a replayed token can be detected and the session revoked. See
[`architecture.md`](architecture.md) → Authentication.

### `catalog_papers`

Papers Atlas knows about but has not read — arXiv metadata harvested in bulk. **The only table
in the schema that is not owner-scoped**: this metadata is public and identical for every
account, so a per-user copy would multiply hundreds of thousands of rows by the number of
accounts to store the same bytes. What stays private is which papers an account has imported,
and that lives in `papers`.

| Group | Columns |
|---|---|
| Identity | `arxiv_id` (unique, version-less), `doi` |
| Bibliographic | `title`, `abstract`, `authors` (JSONB), `categories` (JSONB), `primary_category`, `journal_ref`, `comments`, `published_on`, `updated_on` |
| Search | `search_tsv` |
| Provenance | `harvested_at` |

`search_tsv` is maintained by the trigger `catalog_papers_search_tsv`, not by a generated
column — PostgreSQL only allows immutable expressions in a generated column, and
`setweight(to_tsvector(...))` over two columns is not accepted there. The guarantee that
matters holds either way: nothing in the application writes the column, so nothing in the
application can forget to. Title is weight A and abstract weight B.

Indexes: GIN on `search_tsv` (the one that has to stay fast as the table grows), GIN
`jsonb_path_ops` on `categories` for containment, plus `published_on` and
`(primary_category, published_on)` for browsing.

Filled by `python -m scripts.harvest_arxiv`. See [`decisions.md`](decisions.md) D12 and D13.

### `papers`

One row per document in a user's library.

| Group | Columns |
|---|---|
| Ownership | `owner_id` |
| Bibliographic | `title`, `authors` (JSONB), `abstract`, `publication_year`, `venue`, `doi`, `arxiv_id` |
| Provenance | `source`, `source_url`, `original_filename`, `storage_key`, `content_hash`, `file_size_bytes`, `page_count` |
| Pipeline | `status`, `failure_reason` |
| User state | `reading_status`, `is_favorite`, `last_opened_at` |

Every bibliographic field is nullable: a paper exists from the moment it is uploaded, before
anything has read it, and the UI shows the filename until a real title is known.

`authors` is JSONB rather than a table because Atlas does not attempt author identity
resolution — these are strings in printed order, not entities. Promoting them to a table would
imply a `same person` claim the data does not support.

**`UNIQUE (owner_id, content_hash)`** makes re-uploading a file you already have resolve to the
paper you already have. Scoped per owner, since two users may legitimately hold the same PDF.

### `paper_sections`

The section outline: `ordinal`, `title`, `level`, `page_start`, `page_end`. Gives citations a
locator a person recognises — "§4.2 Results" rather than a character offset.

### `paper_chunks`

The retrieval unit, and the reason citations can be trusted.

| Column | Purpose |
|---|---|
| `content` | The passage |
| `ordinal` | Position in the document, unique per paper |
| `page_start` / `page_end`, `section_id` | Where it came from |
| `token_estimate` | Context budgeting |
| `embedding vector(1536)` | Semantic search; null until indexed |
| `content_tsv tsvector` | Lexical search — **generated**, maintained by PostgreSQL |

`content_tsv` is a generated column rather than a trigger or an application write, because a
code path that forgets to update it produces a search index that is quietly wrong.

Indexes: GIN on `content_tsv`, HNSW (`vector_cosine_ops`) on `embedding` — the two halves of
hybrid retrieval.

**Chunks are immutable once written.** Citations reference chunk ids, so mutating a chunk would
silently change what an existing citation claims. Re-ingesting deletes and rewrites them.

Embedding dimensionality is fixed at the column. Changing embedding model is a migration plus a
re-index, not a configuration change.

### `collections`, `collection_papers`, `tags`, `paper_tags`

Organisation. Both collections and tags are unique per owner, so two users can each have a
"Reading list". `collection_papers` is a model rather than a bare association table so the join
can carry `added_at`.

### `ingestion_jobs`

The queue. One row per ingestion attempt, claimed with `FOR UPDATE SKIP LOCKED`.

| Column | Purpose |
|---|---|
| `status`, `stage`, `progress` | What is happening, and how far along |
| `attempts`, `max_attempts`, `error_message` | Retry budget and the reason for the last failure |
| `scheduled_at` | When the job becomes eligible; retries push it forward |
| `locked_by`, `locked_until` | Lease holder and expiry |

`locked_until` is what makes a crash survivable: a worker that dies leaves a lease that expires,
and the job is reclaimed rather than stranded in `running` forever.

A partial index on `(status, scheduled_at) WHERE status = 'queued'` serves the claim query,
which is the only hot path on this table.

## Deletion

Cascades follow ownership. Deleting a user removes their papers; deleting a paper removes its
sections, chunks, jobs, and collection memberships. `paper_chunks.section_id` is
`ON DELETE SET NULL` rather than cascade — re-ingestion replaces sections, and a chunk should
survive losing its heading rather than vanish from the index.

Stored files are deleted only when no remaining paper references the key, because storage is
content-addressed and two papers can legitimately share one blob.

## Working with migrations

```bash
cd backend
./.venv/bin/alembic revision --autogenerate --rev-id 0003 -m "short description"
./.venv/bin/alembic upgrade head
```

Read every autogenerated migration before applying it. Autogenerate does not detect extensions,
index method changes, or data backfills. The test suite runs a full `downgrade base` →
`upgrade head` cycle, so a broken `downgrade()` fails the suite.

Every model must be imported in `atlas/models/__init__.py` — autogenerate compares against
`Base.metadata`, and a model nothing imports is invisible to it.
